# Linux X11: XTest injection, grabs, XI2; Wayland limits; hotkeys per OS

Sources: XTest extension spec (X11R7.7 `xextproto/xtest.html`, fetched 2026-11-25, quoted
as "spec"); x11rb / x11rb-protocol 0.13.2; winit 0.30.13 `platform_impl/linux/x11`;
global-hotkey 0.10.0; OCM `crates/platform/src/pointer/linux.rs`, `hotkeys.rs`. Linux is
compiled in CI only; nothing here was run on a Linux device.

## XTest fake input (spec; x11rb `xtest_fake_input(type, detail, time, root, x, y, deviceid)`)

- Motion: `root` is the root window where the motion happens; `detail` True = relative,
  False = absolute root coordinates. OCM sends `MOTION_NOTIFY_EVENT`, detail 0, absolute,
  rounded to i16, then `flush()`.
- Buttons: `detail` is the **physical** button, mapped to logical by the current
  `SetPointerMapping` (left-handed users swap). OCM sends button 1 press + release.
- "When the simulated event(s) are processed, they cause event propagation, passive grab
  activation, and so on, just as if the corresponding input device action had occurred";
  motion "might not be recorded in the motion history buffer".
- `time` is a delay in ms, `CurrentTime` = none; "No other requests from this client will
  be processed until this delay" expires. OCM uses `CURRENT_TIME`.
- `GrabControl(impervious)` makes the client keep running during another client's server
  grab. OCM doesn't use it: during a server grab (some WM operations) XTest requests stall.

## What follows from "as if the device did it"

- A faked ButtonPress activates the core automatic pointer grab like a real one (X11
  protocol): the window under the cursor gets all motion until all buttons are up. A real
  press followed by XTest motion: the server merges both into the master pointer, so the
  pressed window should see motion with the button mask set — i.e. drags follow the camera
  without a special event type (expected from the protocol, unverified on device).
- Distinguishing synthetic events: with XInput2 the XTest device is a separate slave
  ("Virtual core XTEST pointer"); XI2 events carry it as `sourceid`. winit reports only
  `deviceid` (master) — not visible to egui. Held-button state (to avoid releasing a physical drag): `QueryPointer`
  `mask` (Button1Mask…) reflects the master pointer, faked presses included (unverified).
- Reading the cursor: `QueryPointer(root)` → `root_x/root_y` in root pixels (OCM
  `raw_position`), same space as RandR monitor rectangles (`randr_get_monitors`, fallback
  root geometry). Monitors can't be negative on X11, but dead zones exist with mixed sizes:
  `geometry::snap` handles them.

## winit on X11

XInput2: `XI_Motion` → `CursorMoved` (window-relative `event_x/y`, only when changed);
`XI_Leave` → `CursorLeft`; buttons skip `XIPointerEmulated` (touch emulation). winit grabs
the pointer only for `CursorGrabMode`, which OCM doesn't use. egui points = window px /
`pixels_per_point`.

## Wayland

No global injection or global cursor read for ordinary clients: `SystemPointer::new`
returns `Unsupported` when `XDG_SESSION_TYPE=wayland` or `WAYLAND_DISPLAY` is set
(`pointer/mod.rs` `is_wayland`, P10/P11). XTest via XWayland reaches only X11 windows, so
it is not a fallback. global-hotkey has no Wayland backend (P12): in-window keys only. Don't
propose portals (RemoteDesktop, GlobalShortcuts) without an ADR; they are new dependencies
and user-visible consent flows.

## Global hotkeys per OS (global-hotkey 0.10.0, `crates/platform/src/hotkeys.rs`)

| OS | Mechanism (source) | Thread | Focus interaction |
|---|---|---|---|
| macOS | Carbon `RegisterEventHotKey`; CGEventTap only for media keys | main run loop | whether the focused window also sees the key: unverified |
| Windows | `RegisterHotKey` on a hidden window, `WM_HOTKEY` | thread with the message loop that created the manager | unverified |
| X11 | `grab_key` on the root, own thread and connection, registered ×4 for NumLock/CapsLock combinations | spawned thread | a passive key grab sends the key to the grabbing client, not the focused window (protocol) |

OCM registers on the event-loop thread inside the eframe creator (`main.rs`) and also
forwards its own windows' key events; `KeyRouter` merges both so one press never toggles
twice. Hotkeys are fixed (AGENTS.md): no configurability without the user.
