# v0.4.1 stabilization roadmap (temporary)

The checklist for the v0.4.1 bug-fix release on `fix/v0.4.1-stabilization`. One slice per
session; tick items in the same commit as the code that does them. The current session state
and next steps are in [`V0.4.1_HANDOFF.md`](V0.4.1_HANDOFF.md). **Both files are deleted
before the merge to `main`** (slice 6), after their decisions and evidence have moved into
the permanent docs, ADRs and tests (ADR-0022 precedent).

Source: the user's v0.4.1 seed brief (Windows test drive at 1920×1080, 2026-11-24). Its items
are **symptoms and audit leads, not diagnoses**. Each slice starts by reproducing the issue
with a test, a replay metric or `OCM_PERF` (AGENTS.md "Measure first").

Legend: `[x]` done · `[~]` started · `[ ]` open · `[?]` needs a user decision · `[-]` dropped/deferred

## Rules for this release

- No merge to `main`, tag, release or website deploy without the user's explicit yes.
- No default, hotkey or visual-direction change without the user's yes (ADR-0006); a changed
  default gets an amendment to the ADR that owns it.
- Windows is the primary platform but **there is no Windows device on the dev machine**:
  nothing is "verified on Windows" unless the user ran it there. Say so in every report.
- Timing the user reasonably needs to tune becomes a setting, not a new hard-coded number.
  Low-level LK/ZNCC/filter tuning stays internal.
- Recordings stay local (diagnosis only); findings become synthetic tests.

## Slice 1 — Tracking continuity (P0)

Leads: `crates/tracking-core/src/lk.rs` (`appearance_rejects`, `reject`, edge holds),
ADR-0018 (anchored appearance gate; 2018 had none), ADR-0011 (tracker defaults).

- [x] Opt-in loss diagnostics: per frame, the loss/hold reason (LK solve, motion outlier,
      forward-backward, appearance gate, frame-edge hold), appearance score, position. No
      imagery logged. Visible via `OCM_PERF`/diagnostics, off by default
      (`Diagnostics::anchor_score`, `perf::TrackLog`, overlay `anchor` line)
- [x] Reproduce "loses the point more easily than 2018" on the user's machine with the
      diagnostics; record which reason fires (numbers stay out of the repo). macOS only
      (session 6, two runs; a Windows run is not possible for v0.4.1, moved to
      `docs/ROADMAP.md`). Every loss was `AppearanceChanged` from the anchored gate; none
      from edges, fast-move holds or LK. Three groups: (1) lag check just under its
      threshold while the selection score and residual looked healthy (most losses);
      (2) both scores low with a high residual on violent moves (real slips, must stay
      losses); (3) selection floor on a far, smooth turn (rare). Re-detection (on in the
      user's settings) resumed every loss of the clean run within ~3 s
- [x] Synthetic fixtures for the three groups (`tests/support` `loss_groups()`, tests in
      `tests/appearance.rs`): `turn_borderline` (keeps tracking), `turn_borderline_long`
      (held 3 frames, then lost), `violent_slip` (lost at once, re-detected), `turn_far`
      (lost at the selection floor: floor unchanged, decided per D4 "don't overdo it")
- [x] Fix per D4: `Held(AppearanceDegraded)` for at most 3 frames when the lag ZNCC is
      0.6–0.7 and the floor holds (ADR-0018 amendment 2026-11-24). A hold, not `Tracking`,
      because `occluder_slide` crosses the band on its first covered frame. No residual
      threshold: the lag band alone separated the groups, and the residual is in absolute
      intensity units (contrast-dependent). `OCM_PERF` counts it as `held look`
- [x] No regression: every corpus and appearance scene unchanged at 320/640/1280, 0 wrong
      locks, 0 false tracking. The pointer jump bound (R-P4) is for re-acquisition only; a
      hold resumes through the smoother
- [-] Real-use check of the hold: deferred to Windows user feedback after v0.4.1 (user,
      2026-11-25), in `docs/ROADMAP.md` App item 1
