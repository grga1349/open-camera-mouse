# v0.4.1 stabilization roadmap (temporary)

Plan, items, statuses, decisions and evidence for the v0.4.1 bug-fix release on
`fix/v0.4.1-stabilization`. Resume state: [`V0.4.1_HANDOFF.md`](V0.4.1_HANDOFF.md). **Both
files are deleted before the merge to `main`** (E9), after the leftovers reconciliation (E8)
has moved their decisions and evidence into the permanent docs, ADRs and tests
(`.agents/PLANNING.md`).

Source: the user's v0.4.1 seed brief (Windows test drive at 1920×1080, 2026-11-24) and the
user's macOS device checks (session 11, 2026-11-25). Its items are **symptoms and leads, not
diagnoses**: every fix starts by reproducing the issue with a failing test, a replay metric or
`OCM_PERF` (AGENTS.md "Measure first").

Layout (`.agents/PLANNING.md`, ADR-0025 amendment 2026-11-25): the plan reads top to bottom in
execution order; priority is on each item. Ids were renumbered in plan order on 2026-11-25
(user); the handoff of that session maps old → new.

Legend: `[ ]` open · `[~]` in progress · `[?]` blocked (on what) · `[i]` implemented,
verification owed · `[x]` done · `[>]` deferred (where to) · `[-]` dropped (why, who).
Priority: `P0` blocks the release · `P1` belongs in it, may move to Leftovers with the user's
OK · `P2` nice to have.

Verification levels: **auto** = tests and gates locally plus CI on macOS, Windows, Linux;
**device** = a user run on a named OS; **input** = physical button vs. dwell; **camera** =
built-in vs. external.

## Rules for this release

- No merge to `main`, tag, release or website deploy without the user's explicit yes.
- No default, hotkey or visual-direction change without the user's yes (ADR-0006); a changed
  default gets an amendment to the ADR that owns it.
- Windows is the primary platform but **there is no Windows device on the dev machine**:
  nothing is "verified on Windows" unless the user ran it there. Say so in every report.
  Windows device checks are batched into the user's Windows run (E6).
- Timing the user reasonably needs to tune becomes a setting, not a new hard-coded number.
  Low-level LK/ZNCC/filter tuning stays internal.
- Recordings stay local (diagnosis only); findings become synthetic tests.
- Only the user makes or unmakes a release blocker.
- Already decided by the user (brief): dwell-time default stays **1 s**; dwell time allows
  exactly **0.25 s**. No Windows `OCM_PERF` run for v0.4.1 (deferred to `docs/ROADMAP.md`).

## Phase A — Clicking under camera control

Method per fix, one per session: failing reproduction test at the lowest layer that shows it
(pointer-core / controller rig / engine with a fake echoing pointer / kittest with the logged
event sequences) → kept tests of the correct behaviour → fix → independent review (native
input semantics, `.agents/WORKFLOW.md` "Review") → the symptom re-checked by the user on macOS. Windows/Linux: CI only, say
so. Diagnostics: `OCM_INPUT=1` (`apps/desktop/src/input_log.rs`, `TESTING.md`), logs stay
local.

- [~] **A1 A gain change keeps the cursor where it is** (P0; S1, plausibly S4; includes the
      Windows slider report, merged by the user 2026-11-25). Cause (confirmed by tests):
      `map_raw_scaled` scales `(p + offset − frame/2)` around the desktop centre and
      `update_settings` kept `offset`, so the cursor jumped to `centre + distance · new / old`
      and a speed slider dragged by the head fed the jump back into its value. With the
      default steady zone a decrease still pulled the cursor up to 11 px (review). Fix:
      re-anchor the mapping so the last filtered head point lands on the cursor sent
      (`pointer_core::offset_mapping_to`); smoother and zone restart there.
      Accept: changing gain_x, gain_y or both (linked) while Tracking moves the cursor < 1 px;
      a speed-slider drag driven by the head converges; later head motion uses the new gain;
      on Windows, speed, smoothing and dwell sliders set and hold their value under a physical
      press-drag with the camera in control, keyboard control works, values persist across a
      relaunch. Verify: done, auto local: controller tests
      `a_gain_change_keeps_the_cursor_where_it_is`,
      `…_with_the_default_smoothing_and_steady_zone`,
      `a_speed_slider_driven_by_the_cursor_settles_instead_of_swinging` (all failed before),
      `head_motion_after_a_gain_change_uses_the_new_gain`, pointer-core inverse test. The
      kittest slider drag (and the merged Windows report's custom-widget/plain-slider kittest)
      is dropped (user, 2026-11-25: the controller loop test covers it).
      CI green for `d58a1a3` (macOS, Windows, Linux).
      Independent re-review found an unsettled-filter gap: after one head step, changing
      gain 20 → 60 amplified the filter's residual motion on identical subsequent frames
      (140.91 px versus 91.08 px without the gain change, synthetic probe). Remaining:
      reproduce in a committed regression test, correct and independently review; S1/S4 in
      A6 (macOS, physical button); the Windows criteria in E6
- [~] **A2 A dwell click (press+release in one egui pass) sets a slider** (P0; S2).
      Evidence (traced, reproduced off-repo): egui 0.37 `interaction.rs:157` treats a
      same-frame press+release as no drag; `Slider` senses drag only (`slider.rs:594`), so
      `interact_pointer_pos()` stays None and the value is unchanged (`slider.rs:532`).
      egui-winit batches a redraw's events into one `RawInput`, and a dwell click posts
      down+up back to back, so both likely land in one pass (not yet seen on the device). The kittest
      `a_click_on_a_slider_rail_sets_the_value_there_in_one_pass_or_two` misleads:
      `Harness::step` runs one frame per queued event, so its "same pass" case is two passes.
      Off-repo, one `RawInput` holding both events left a `Slider` at 0; a `Sense::click`
      widget still got `clicked()`. Fix options (fix session decides): a gap between the
      posted down and up, or a slider that also senses click.
      Accept: press+release in one pass on any of our slider rails sets the value at that
      point; the misleading kittest is corrected. Verify: kittest queuing both events via
      `input_mut().events` in one pass (fails today); S2 in A6. The corrected test fails
      against unchanged production code (20 instead of 15). Two fixes were rejected: adding
      click sense to the slider lost a quick drag's final position; a separate click target
      made a focused slider lose keyboard focus. Both experiments were removed. Remaining:
      a new same-ID click/drag experiment restored quick drags and long-touch capture but
      left a click claim after Escape, changing a slider on subsequent small movement;
      independent review reproduced this and the experiment was removed. Focus, long-touch
      and Escape regression tests now guard the original behavior. Reassess the design before
      another attempt, then test, implement and independently review.
