# v0.4.1 stabilization roadmap (temporary)

Plan, items, statuses, decisions and evidence for the v0.4.1 bug-fix release on
`fix/v0.4.1-stabilization`. Resume state: [`V0.4.1_HANDOFF.md`](V0.4.1_HANDOFF.md). **Both
files are deleted before the merge to `main`** (6.8), after the leftovers reconciliation has
moved their decisions and evidence into the permanent docs, ADRs and tests (ADR-0022
precedent, `.agents/PLANNING.md`).

Source: the user's v0.4.1 seed brief (Windows test drive at 1920×1080, 2026-11-24). Its items
are **symptoms and audit leads, not diagnoses**: every fix starts by reproducing the issue
with a failing test, a replay metric or `OCM_PERF` (AGENTS.md "Measure first").

Legend (`.agents/PLANNING.md`): `[ ]` open · `[~]` in progress · `[?]` blocked (on what) ·
`[i]` implemented, verification owed · `[x]` done · `[>]` deferred (where to) · `[-]` dropped
(why, who). Ids are stable (`2.3`, `F1`, `D4`); sub-ids (`2.3a`) mark splits.

Verification levels (named per item where they matter): **auto** = tests and gates locally
plus CI on macOS, Windows, Linux; **device** = a user run on a named OS; **input** = physical
button vs. dwell; **camera** = built-in vs. external. An item without `Verify` still needs
CI green on all three OSes, plus a device check if the behaviour is device-only.

## Rules for this release

- No merge to `main`, tag, release or website deploy without the user's explicit yes.
- No default, hotkey or visual-direction change without the user's yes (ADR-0006); a changed
  default gets an amendment to the ADR that owns it.
- Windows is the primary platform but **there is no Windows device on the dev machine**:
  nothing is "verified on Windows" unless the user ran it there. Say so in every report.
  Windows device checks are batched into the user's acceptance run (6.2).
- Timing the user reasonably needs to tune becomes a setting, not a new hard-coded number.
  Low-level LK/ZNCC/filter tuning stays internal.
- Recordings stay local (diagnosis only); findings become synthetic tests.
- Only the user makes or unmakes a release blocker. "Blocks release: proposed …" below is the
  planner's proposal, **user decides**.
